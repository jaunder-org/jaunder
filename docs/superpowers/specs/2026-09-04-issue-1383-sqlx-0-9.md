# SQLx 0.9 Upgrade

## Outcome

Jaunder uses SQLx 0.9 throughout its first-party host dependency graph while
preserving its existing SQLite and PostgreSQL behavior, schemas, persisted
values, and public behavior. This establishes the dependency foundation needed
by issue #1272 without beginning the Chrono-to-Jiff migration.

## Load-bearing decisions

- The workspace SQLx dependency moves from the 0.8 series to the 0.9 series.
  Every first-party crate consumes that workspace version; the resolved lockfile
  contains no SQLx 0.8 package.
- Existing SQLx features remain semantically unchanged: SQLite and PostgreSQL
  drivers, migrations, Tokio runtime integration, and Chrono support stay
  enabled until issue #1272 changes the time-library boundary.
- The lockfile remains the dependency-resolution authority. Nix continues to
  derive its vendored sources and offline Cargo homes from it; no checked-in
  vendor tree or second dependency-resolution mechanism is introduced.
- The development-shell `sqlx-cli` remains development-only. Its nixpkgs-owned
  version is audited for compatibility, but it does not become a CI or product
  dependency.
- No `sqlx.toml` or `.sqlx` metadata is adopted unless SQLx 0.9 demonstrably
  requires it to preserve existing behavior. SQLx query macros remain forbidden
  under `storage/src` per ADR-0169.
- The generic storage architecture from ADR-0019 remains intact. SQLx 0.9's
  lifetime-free `Arguments` and `IntoArguments` forms replace the obsolete 0.8
  bounds exactly where stores, dialects, and typed query extensions require
  them; common bounds do not move onto `Backend`.
- The sealed `StorageBind` registry remains the only normal value-admission
  boundary. SQLx 0.9 adaptation must not add raw binds, prebuilt-argument escape
  paths, primitive admissions, query macros, allocation, conversion, cloning,
  retained query state, or runtime dispatch.
- The central derive implementation remains the sole owner of generated SQLx
  bridges. Generated `Type`, `Encode`, `Decode`, and opt-in PostgreSQL array
  implementations retain their current validation, storability, feature
  isolation, and backend-generic behavior under SQLx 0.9.
- SQLx stays outside the wasm dependency graph. The existing compile-time guard
  against enabling `common/sqlx` for wasm remains effective.
- Every runtime-built SQL statement is reviewed against SQLx 0.9's `SqlSafeStr`
  contract. Data values are bound rather than interpolated.
- Runtime SQL that must contain structural fragments is approved with
  `AssertSqlSafe` only at the narrow subsystem seam that owns construction and
  can establish the fragments' provenance. Production gains no generic helper
  accepting arbitrary `String` or `&str` as safe SQL.
- Structural fragments are limited to fixed SQL, dialect-owned constants,
  generated placeholders, and identifiers or utility-statement literals that are
  correctly quoted for their backend. Approval never substitutes for binding,
  validation, or escaping.
- Test-only unrestricted fixture SQL may be approved once at the existing raw
  execution helper boundary. Test helpers that interpolate ordinary data use
  binds instead; other test-only structural SQL follows the same explicit
  provenance and quoting rules as production.
- No custom static allowlist governs `AssertSqlSafe` locations. SQLx compilation
  supplies the required-marker census; local assertions, the absence of a
  generic production escape hatch, behavioral tests, and review supply the
  policy check without a file-layout maintenance burden.
- Migration construction and execution adapt to SQLx 0.9 without changing the
  ordered migration corpus, checksums, transactional policy, migration table,
  fresh-database result, or historical-upgrade result.
- SQLite retains its current connection and transaction semantics, including
  foreign-key enforcement, WAL mode, busy timeout, cache settings, and the
  ADR-0021 prohibition on read-then-write deferred transactions.
- PostgreSQL connection resolution retains password-file behavior, redaction,
  slow-statement logging, and error-source behavior. SQLx 0.9's automatic
  PostgreSQL option escaping is audited so Jaunder neither double-escapes nor
  weakens escaping.
- Backend-specific backup and restore implementations remain separate as
  required by ADR-0019. Their catalog inspection, JSON representation, restore
  binding, constraint handling, rollback, and sequence repair behavior remain
  unchanged.
- Public error masking and internal SQLx source chains remain consistent with
  ADR-0017. The upgrade does not reclassify database failures.
- Documentation whose accepted SQLx type signatures become obsolete is updated
  to state the SQLx 0.9 forms without changing the architectural decisions.
- This dependency/API adaptation is not a new architectural decision; it does
  not create a new ADR or alter the domain glossary.

## Acceptance

- The workspace manifests and resolved lockfile use SQLx 0.9 exclusively across
  `common`, `host`, `server`, `storage`, and `web`; SQLx 0.8 is absent.
- Nix evaluates and builds the lockfile-derived vendored and offline dependency
  inputs without network access during Cargo checks.
- Host and wasm builds preserve the existing SQLx feature boundary, including
  the wasm compile guard.
- Macro expansion tests and compiled dual-backend storage tests demonstrate that
  generated domain-newtype `Type`, `Encode`, and `Decode` implementations retain
  their current behavior. PostgreSQL array capability remains opt-in.
- The typed storage-bind compile contracts and residual source check pass with
  no new raw value-admission path.
- Every SQLx 0.9 dynamic-query call compiles through an explicit, reviewed
  safety boundary. Searches and conformance review find no generic production
  escape hatch and no interpolated ordinary data approved as SQL text.
- Every non-bindable runtime identifier or utility-statement literal is quoted
  with the backend-correct rule. Regression cases containing each backend's
  quote or literal delimiter demonstrate that approval cannot hide malformed or
  injectable structural SQL.
- Static and dynamic Post, Syndication Feed, visibility, feed-event, catalog,
  bootstrap, backup, and restore queries return the same results and preserve
  existing bind ordering on both backends.
- Fresh SQLite and PostgreSQL databases migrate to the same schemas as before.
  Historical migration fixtures preserve their existing transformations and
  failure-without-mutation behavior.
- Cross-backend backup/restore, full-cycle backup, restore validation, identity,
  timestamp, media, constraint, and rollback tests pass unchanged in meaning.
- Transaction tests preserve rollback, writer release, atomic mutation,
  confirmed commit, and indeterminate acknowledgement behavior on both backends.
- SQLite connection behavior and PostgreSQL password/option escaping remain
  covered by their existing focused tests or equivalent observable regression
  coverage where SQLx 0.9 changes the exercised API.
- Repository static checks, host tests, dual-backend coverage, wasm checks,
  Nix/offline checks, documentation checks, and the full backend-by-browser CI
  surface pass.

## Boundaries

- No Chrono-to-Jiff migration, time representation change, or `jiff-sqlx`
  adoption; issue #1272 owns those changes.
- No database schema, migration-history, persisted-value, backup-format, or
  wire-format change.
- No redesign of storage traits, `Backend`/`Dialect`, dependency injection,
  typed bind admission, decode policy, transaction ownership, or backup
  architecture.
- No new SQL query framework, generic dynamic-SQL wrapper, or maintained
  `AssertSqlSafe` location allowlist.
- No unrelated query cleanup, storage feature, or dependency upgrade beyond
  changes required for SQLx 0.9 compatibility and preservation of the stated
  behavior.
