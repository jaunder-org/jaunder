## Outcome

Remove the bundled SQLite advisory failure by resolving `libsqlite3-sys` to
fixed 0.39.1, which bundles SQLite 3.54.1.

Do so without an advisory waiver, forced incompatible resolution, feature-mode
workaround, or application behavior change. Keep SQLite as the default backend
and preserve existing SQLx SQLite/PostgreSQL feature parity.

**Approved approach: temporarily path-patch the published normalized
`sqlx-sqlite 0.9.0` crate, changing only its `libsqlite3-sys` bound to
`<0.40.0`, then resolve to 0.39.1.** This is an exact, one-manifest-line
remediation from the checksum-verified released crate and avoids the upstream
git workspace's SQLx-core path identity split. It requires the exact retained
source subset and explicit source-filter maintenance until a compatible SQLx
release is published. The ~408 KB / 58-file measurement is the full
published/cache inventory upper bound, not the selected retained subset size.

## Approach and tradeoffs

### Advisory, release and exact upstream change

- RustSec marks `libsqlite3-sys >=0.39.0` fixed; 0.39.1 is preferred and bundles
  SQLite 3.54.1. References:
  [RustSec advisory](https://github.com/RustSec/advisory-db/blob/main/crates/libsqlite3-sys/RUSTSEC-2026-0459.md),
  [crate index](https://index.crates.io/li/bs/libsqlite3-sys),
  [SQLite issue](https://sqlite.org/bugs/info/2026-08-17T15:54:41Z),
  [SQLite 3.54.0 release](https://sqlite.org/releaselog/3_54_0.html).
- The current resolved graph is `libsqlite3-sys 0.37.0` with `bundled` active
  through `sqlx-sqlite/bundled` and SQLx's `sqlite` / `sqlite-bundled` features.
  `jiff-sqlx` also enables SQLite. This is not a system-SQLite-only graph;
  changing backend mode is outside scope.
- The released
  [SQLx v0.9.0 sqlite manifest](https://github.com/launchbadge/sqlx/blob/v0.9.0/sqlx-sqlite/Cargo.toml)
  declares `libsqlite3-sys >=0.30.1, <0.38.0`, so a lock-only update to 0.39.1
  is invalid.
- SQLx [PR #4502](https://github.com/transact-rs/sqlx/pull/4502), exact
  [commit `10462fa4414c6c7f1ed1d39bb31678e3b726878c`](https://github.com/transact-rs/sqlx/commit/10462fa4414c6c7f1ed1d39bb31678e3b726878c),
  changes one line in one file relative to its parent: `sqlx-sqlite/Cargo.toml`
  from `<0.39.0` to `<0.40.0`.
- The release-relative bound delta is `<0.38.0` to `<0.40.0`; do not confuse the
  one-line commit-parent change with the total change from v0.9.0.
- The current [SQLx index](https://index.crates.io/sq/lx/sqlx) and
  [`sqlx-sqlite` index](https://index.crates.io/sq/lx/sqlx-sqlite) still have no
  release after 0.9.0.

### Full upstream snapshot is not the narrow fix

- GitHub's
  [v0.9.0-to-commit comparison](https://api.github.com/repos/launchbadge/sqlx/compare/v0.9.0...10462fa4414c6c7f1ed1d39bb31678e3b726878c)
  reports 49 commits, 135 changed files, 5,079 additions and 735 deletions
  (5,814 changed lines).
- These are reported diff counts, not a semantic audit of those changes. The
  snapshot is much larger than the needed single manifest bound; do not pin the
  complete SQLx workspace for this advisory.
- A git patch for only `sqlx-sqlite` is not recommended: at the exact git
  revision, `sqlx-sqlite` inherits `sqlx-core` as
  `{ version = "=0.9.0", path = "sqlx-core" }`. That driver then pulls
  git-source `sqlx-core`, while registry SQLx/macros may resolve registry core.
  Cargo package identity includes source, so same name/version is not the same
  package/type identity.
- SQLx macros, macro-core and driver crates have workspace/path relationships
  too. Do not assume only the patched driver changes source identity, or accept
  a split SQLx type graph without a resolver proof.

### Immediate released-source patch candidate

- The cached source directory
  `/home/mdorman/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/sqlx-sqlite-0.9.0`
  is inspected evidence, not the copy origin. Use the checksum-verified
  published `.crate` archive as the canonical origin: SHA-256
  `488e99c397a62007e4229aec669a179816339afc6d2620ca6fa420dbee2e982c`, matching
  the current lock entries.
- Retain exactly its normalized `Cargo.toml`, the complete unchanged `src/`
  tree, `LICENSE-MIT`, and `LICENSE-APACHE`. The sole source change is the
  normalized manifest's `libsqlite3-sys` bound from `<0.38.0` to `<0.40.0`; do
  not modify any Rust source or other manifest metadata.
- Exclude `Cargo.toml.orig`, the crate's nested `Cargo.lock`, `.cargo-ok`,
  `.cargo_vcs_info.json`, and other archive/cache metadata. Preserve both
  licenses and all upstream copyright notices.
- The 58-file / 407,895-byte (~408 KB) figure describes the full published/cache
  inventory and is an upper bound, not a count or size promise for the selected
  retained subset. The inventory includes no C source, native headers or build
  script; there is no separate SQLite C vendoring tree.
- The normalized manifest declares `build = false`,
  `license = "MIT OR Apache-2.0"`, and registry
  `sqlx-core = { version = "=0.9.0" }` with no path. This preserves registry
  identity for core/facade/macros while a local path package replaces only
  `sqlx-sqlite`; the license expression is already allowed by `deny.toml`.
- A path patch changes the package source identity for `sqlx-sqlite` to local in
  each workspace; its `sqlx-core` dependency stays registry `=0.9.0`. The three
  existing graphs each show one resolved `libsqlite3-sys`; it owns SQLite's
  native `links` identity. Confirm uniqueness after the approved resolution
  rather than infer it from versions alone.
- `jiff-sqlx 0.2.0` depends on the SQLx facade and enables SQLite in root/tools;
  read-only trees confirm the patched driver is reached through that same
  facade. Preserve this single registry facade/core/macros identity in all three
  independent workspaces.

### Prospective files, Nix closure and maintenance cost

- All three workspaces already have `[patch.crates-io]` sections and all three
  locked/offline dependency trees reach `sqlx-sqlite`. Root `Cargo.toml`,
  `tools/Cargo.toml`, and `xtask/Cargo.toml` each need a local patch entry to
  the one retained source copy. Root uses a `vendor/sqlx-sqlite-0.9.0`-style
  path; the two nested workspaces would refer to that same checkout path from
  their manifest locations.
- All three locks are affected and need reviewed resolution: root `Cargo.lock`,
  `tools/Cargo.lock`, and `xtask/Cargo.lock`. Current offline trees show
  SQLx/sqlx-sqlite and `libsqlite3-sys 0.37.0` are reachable in every workspace;
  root/tools also show `jiff-sqlx`. Each lock must lose the registry package
  checksum/source for the path-patched driver and select fixed `libsqlite3-sys`;
  actual lock diff remains uncomputed until authorized.
- Cargo local path dependencies are checkout source, not registry-vendored
  packages. The Nix source filters select workspace members and will not
  automatically admit an unrelated vendor crate. Add explicit source admission
  for its parent directories (for traversal), Cargo manifest, complete Rust
  `src/`, and both license files in `nix/packages.nix` product/tools source
  filters and `nix/xtask.nix`'s `sourceAdmits` filter. Exclude
  `Cargo.toml.orig`, nested crate `Cargo.lock`, VCS metadata, and `.cargo-ok`;
  retain only the approved normalized manifest, complete unchanged source tree,
  and both licenses.
- The local-source route adds no upstream Git source, so it does not require a
  `transact-rs` git allowlist, flake input, `flake.lock` narHash, or
  `vendorPinnedFork` override. Nix consumes the retained files through the
  Git-backed checkout source after they are part of the approved tree. Cargo's
  path package has no registry checksum; the published archive checksum is
  evidence of origin, not a replacement lock hash. Its actual checkout source
  and Cargo lock changes still need normal review; no tree hash or checksum is
  guessed.
- `deny.toml` must gain no advisory ignore or waiver. Existing `jaunder-org`
  source allowance is unrelated; a local path patch is not a new Git source
  exception. The copied crate's `MIT OR Apache-2.0` license is already
  permitted.
- Keep the temporary patch only until a released SQLx version whose published
  manifest permits the fixed crate is available. Then remove all three patch
  entries, the retained crate source and its Nix admission exceptions together,
  and update affected locks to the released SQLx source. The release source must
  be verified first; changed source/bounds/graph require renewed approval. This
  gives the copied source a specific removal trigger rather than open-ended fork
  ownership.
- Compared with waiting, the local patch can unblock the advisory gate sooner
  but costs a ~408 KB source copy, three manifest entries, up to three lock
  updates, and explicit Nix filter maintenance. Waiting has no repository
  machinery or copied source but leaves the current gate blocked for an unknown
  upstream release interval. **The recommendation accepts the bounded copy cost
  to avoid indefinite gate blockage.**

## Acceptance

Acceptance for the implementation authorized by the recorded approvals and
approved outline:

1. Use the checksum-verified published `.crate` archive as origin; retain only
   normalized `Cargo.toml`, unchanged complete `src/`, and both licenses. Change
   only the manifest bound from `<0.38.0` to `<0.40.0`; stop if other source
   modifications are required.
2. Resolve all three workspaces without forcing versions. Inspect package IDs
   for SQLx, sqlx-core, sqlx-macros, sqlx-macros-core, sqlx-sqlite and
   jiff-sqlx; show one compatible facade/core/macros identity per workspace and
   local identity only for sqlx-sqlite.
3. Show `libsqlite3-sys 0.39.1` and bundled SQLite 3.54.1 in each affected
   lock/feature graph, with no duplicate native `links` package or incompatible
   duplicate SQLx types.
4. Prove Nix source filters admit the exact retained crate files in product,
   tools and xtask sources and that normal offline vendoring still resolves its
   registry dependencies. No Git source, guessed hash or network fallback.
5. Run cargo-deny advisories without a new ignore/waiver, then normal repository
   hooks and current required CI. Preserve existing SQLite/PostgreSQL storage,
   migration, backup/restore and E2E behavior using existing tests; add no
   database framework or exploit matrix.
6. Keep this central security repair separate from #1921's consumer patch.
   Remove the temporary local source/patch when a compatible upstream release is
   adopted.

## Boundaries

- Implement only the approved local-source patch, three workspace patch/lock
  resolutions, required Nix source admission, and named verification. The
  normalized `Cargo.toml` bound is the sole source modification; do not change
  Rust source, application behavior, schema, API, features or backend mode. No
  advisory waiver, forced dependency, false metadata, guessed hash, blanket lock
  refresh, or new framework.
- No whole SQLx-main snapshot pin, unsafe git-only package patch, incompatible
  dependency force, false version metadata, advisory waiver, system-SQLite
  workaround, blanket lock update, guessed hash, new fork framework or
  suppressed gate.
- This approved tracked spec is
  `docs/superpowers/specs/2026-11-09-issue-1928-rustsec-2026-0459.md`; maintain
  it through implementation and conformance review, then remove it in the final
  planning-document cleanup commit.
- If a compatible registry release or any other approved input changes before or
  during implementation, stop for renewed human decision; do not silently switch
  source, bound, or lock graph. Each PR merge remains separately gated by scoped
  human approval.
