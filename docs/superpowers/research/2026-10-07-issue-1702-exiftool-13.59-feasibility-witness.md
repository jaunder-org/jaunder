# #1702 task 1 — bounded ExifTool and ICC feasibility witness

**Status: still incomplete.** This is fixture/probe evidence only; it adds no
runtime dependency, `MediaManager`, HTTP behavior, or public sanitizer API.

## Reproduction and provenance

```sh
devtool run -- nix build --impure --out-link .xtask/image-metadata-witness \
  --print-out-paths --file testdata/image-metadata-sanitizer/probe.nix
```

The output is retained at the gitignored `.xtask/image-metadata-witness` link,
so focused inspectors can reuse fixtures without garbage collection removing an
unrooted intermediate. The command prints the exact store path for that run. It

The fixture image is an owned generated 32×24 gradient, and all image metadata
values are synthetic. `make_icc_fixture.c` generates the ICC fixture at build
time from pinned LittleCMS's `linkicc` output; it deliberately stamps synthetic
header timestamp, manufacturer (`JAUD`), model (`TEST`), and creator (`OWND`),
and writes English and French `mluc` description/copyright records. It is not a
claim that the embedded text of a third-party profile is a license. The tested
format-specific scope is only an owned RGB-to-XYZ ICC v4 device-link profile
with exactly `A2B0`, `wtpt`, `desc`, `cprt`, `pseq`, and `psid` tags. ICC v2
(and every other version, class, colour space, tag type, shared/overlapping
extent, or tag set) is rejected. The v2 negative control is accepted only when
its stderr contains exactly `ValueError: only ICC v4 profiles are supported` and
no output artifact exists; import, syntax, I/O, or other failures fail the
witness.

## Machine-checked evidence

`probe.nix` fails on unexpected rewrite, decode, render, repeated-input,
second-pass, or independent-verifier failure. It preserves the generic ExifTool
candidate failure as positive evidence: this command retains an unchanged ICC
when instructed to retain it:

```sh
exiftool -overwrite_original -all= --icc_profile:all candidate.jpg candidate.heic
```

The stdlib-only `verify.py` now asserts, rather than merely reports:

- the bounded single-scan JPEG's entropy scan is unchanged and its
  GPS/descriptive/XMP/IPTC/thumbnail marker classes are gone;
- the generic retained-ICC candidate is an expected privacy failure;
- same-input processing invokes the full JPEG pipeline in two separate
  single-file ExifTool process pairs, then compares bytes; this is separate from
  second-pass byte idempotence;
- the fixture-scoped HEIC has exactly one of each required meta child (duplicate
  children reject), strict child-bounded `iloc` consumption with applied
  `base_offset`, one extent/item, construction method zero and
  `data_reference_index == 0`. `pitm` identifies the `hvc1` primary item and
  `iinf` identifies the `Exif`/`mime` descriptive items by ID; exact typed
  payloads and the `cdsc` graph are then compared. Out-of-envelope shapes
  reject;
- the format-specific ICC rewrite removes `desc`, `cprt`, `pseq`, and `psid`,
  zeroes timestamp/device maker/model/creator/profile-ID/reserved header fields,
  keeps only allowed `A2B0`/`wtpt`, and embeds that rewritten profile in the
  JPEG without changing JPEG scan bytes;
- `validate_icc.c`, a separately compiled LittleCMS consumer, can open both
  profiles and yields identical RGB-to-XYZ values for 4,096 samples. The
  retained `A2B0` transform bytes also hash identically;
- the ICC scrubber itself reprocesses its rewritten output byte-identically in
  the supported profile envelope. This proves scrubber idempotence, not a
  general sanitized-upload reupload policy.

## Ordinary RGB ICC extension

Pinned LittleCMS generates four owned monitor profiles: sRGB and P3 primaries
with **gamma 2.2, not the standard Display-P3 transfer function**, each encoded
as ICC **2.0 or 4.0**. The legacy `display-p3` fixture filename denotes that
P3-primary/gamma-2.2 control only. Source headers use synthetic creation date
`2026-10-07T12:34:56`, manufacturer/model `JAUD`/`TEST`, and creator `OWND`. The
v4 descriptions have English/French `mluc` records; v2 uses legacy `desc`/`text`
with counted Unicode. No external profile or asset license is introduced. Pinned
LittleCMS 2.19.1 counts alignment padding in its v2 `desc` table size. The owned
fixture generator corrects that one table size to exclude padding, without
changing offsets or transform bytes. This is a disclosed fixture construction
step, **not** a malformed-user-input repair path.

The declared envelope requires exactly eleven tags: `desc`, `cprt`, `wtpt`, RGB
colourants/TRCs, **both `chad` and `chrm`**. Absence of adaptation is not
accepted on an unproven assumption. Tags must be word-aligned and packed; exact
shared extents are preserved, partial overlaps and nonzero gaps/padding reject.
`rewrite_rgb_icc.py` bounds profile input to 8 MiB and checks the entire version
encoding, class/spaces, calendar date, flags/attributes, intent, PCS D50 and
reserved header fields. It checks XYZ cardinality, positive media white and
nonsingular RGB/adaptation matrices, curve counts, positive gamma, nonconstant
nondecreasing sampled curves, parametric function-specific lengths and admitted
gamma/scale/slope/threshold ranges, chromaticity records, and
reserved/body/padding fields. It does not certify arbitrary device calibration
or interoperability beyond these fixtures.

Required `desc`/`cprt` remain, with deterministic neutral `desc`/`text` (v2) or
single-record `mluc` (v4) bodies. Counted v2 ASCII/Unicode are decoded and
terminated correctly; the complete 70-byte ScriptCode section is consumed. The
accepted legacy-script form is empty, code zero. v4 admits at most two unique,
contiguous locale records with bounded, valid UTF-16 strings. Arbitrary record
layouts, scripts, versions, vendor tags and LUT profiles reject. Output date is
valid non-personal boilerplate `2000-01-01T00:00:00`, not the source creation or
capture time. CMM, platform, device, creator, ID and reserved identifiers are
cleared; transform-bearing bytes remain unchanged.

`verify_rgb_icc.py` uses its own advancing bounded reader, **without importing
the canonicalizer**, to consume admitted bodies and independently assert exact
neutral values, record counts/offsets/lengths, header semantics and
whole-profile padding. `verify_rgb_structure_controls.py` tests both malformed
source rejection and deliberately corrupted output rejection, including direct
body truncation/suffix controls so table rejection cannot mask a shallow body
reader. The suite makes **636 checks** across the four profiles:
mandatory/duplicate tags, versions/header/date, each admitted type/reserved
field, internal counts, Unicode/locale/string bounds, overlap/gaps/padding,
singular matrices, and output identifier leaks. Expected failures must be typed
ICC-domain rejection, not syntax/import/I/O failures, and must leave no output.
Positive shared-TRC and 14-byte gamma-versus-word-padding controls also run.
Type-defined body lengths must match table extents exactly: alignment bytes live
outside those extents, even when zero. Full-profile controls enlarge all shared
aliases together to absorb padding and require rejection by both readers.

For each profile, the JPEG pipeline extracts the actual embedded profile,
rewrites that extraction and reinserts its own result. Separate invocations on
the original prove deterministic bytes; reprocessing its own output proves
idempotence. The independent verifier compares all four compressed scans,
complete output profiles and unchanged semantic header/transform bytes. A
separate LittleCMS consumer compares four intents over 4,096 RGB samples each.

Primary structural references:
[ICC.1:2010 v4.3](https://www.color.org/specification/ICC1v43_2010-12.pdf)
(type/header layouts, including legacy description fields), the ICC's
[missing-required-tag guidance](https://www.color.org/security/malformed/missing-required/)
and [matrix/TRC FAQ](https://www.color.org/faqs/). These inform the narrow
reader; a passing fixture/consumer comparison is **not** general ICC
certification.

## Remaining barriers

The generated HEIC is not a real-device proof. It has `nclx`, not embedded ICC,
and lacks thumbnail/preview and auxiliary/depth graph cases. Real-device-
structure representative, non-personal/provenanced fixtures and all retained
HEIF item/reference validation remain required. PNG/APNG, GIF, WebP, other JPEG
shapes, other ICC profile classes/versions, and complete accepted/rejected HEIF
envelope work are also untouched. Do not mark task 1 complete or integrate
upload ingress from this witness.
