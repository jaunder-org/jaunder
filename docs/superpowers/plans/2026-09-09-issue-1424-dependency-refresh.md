# Dependency Refresh Implementation Outline

> Execute with `jaunder-iterate`, using `jaunder-dispatch` for isolated slices.
> This outline exists because the repository-wide refresh has multi-agent
> contracts across Cargo, Nix, npm/Playwright, and CI version sources.

## Scope

In:

- Freeze and record the approved implementation-start version snapshot.
- Refresh every build/runtime pin, generated dependency lock, compatibility
  baseline, and directly required compatibility change named by the spec.
- Re-evaluate temporary forks, prereleases, and source overrides against their
  accepted ADR exit conditions.

Out:

- Product features, public protocol or persistent application-data changes.
- New dependency automation or support-window policy.
- Opportunistic refactors and unapproved architectural migrations.

## Ordering and parallelism

- Task 1 gates every implementation task.
- Task 2 is the sole owner of Atom's coupled Cargo and Nix identity and lands it
  atomically before the broad Cargo refresh.
- After Task 2, Tasks 3 and 5 may run in parallel. Task 4 starts after Task 2
  because refreshed nixpkgs is the Playwright source of truth; it may run in
  parallel with Tasks 3 and 5.
- Task 6 starts after Tasks 2–5 and is the sole integration boundary.

## Risk checks

- No selected version silently drifts after the snapshot or lacks a recorded
  case-by-case disposition.
- Atom, lettre, leptosfmt, diagnostic-nightly/minicov, wasm-bindgen CLI/runtime,
  and Playwright coupled pins satisfy their current ADR invariants or remove the
  obsolete workaround completely.
- Generated locks and hashes come from their owning tools; none is hand-edited.
- The root, `xtask`, and `tools` Cargo workspaces remain separate and all retain
  their compensating host coverage.
- NixOS module options and process behavior, Playwright's single configuration,
  browser provenance, CI merge-queue behavior, and application-visible behavior
  remain unchanged despite advancing their version baselines.
- Any required architecture, protocol, persistent-data, or product-behavior
  change stops for an explicit scope decision before implementation continues.
