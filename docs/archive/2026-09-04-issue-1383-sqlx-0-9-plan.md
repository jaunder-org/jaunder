# SQLx 0.9 Upgrade Implementation Outline

> Execute with `jaunder-iterate`, using `jaunder-dispatch` for independently
> owned slices. This outline exists because storage-dialect behavior, migration
> compatibility, and runtime SQL safety carry non-obvious cross-backend risk.

## Scope

In:

- SQLx 0.9 dependency resolution, generic API adaptation, and generated bridges.
- Runtime SQL safety migration across production and test code.
- Migration, connection, backup/restore, and transaction parity for SQLite and
  PostgreSQL.
- Lockfile-derived Nix/offline inputs and accepted SQLx signature documentation.

Out:

- Chrono-to-Jiff work, schema or persisted-value changes, storage redesign,
  query macros, `sqlx.toml`, and unrelated dependency upgrades.
- A generic production dynamic-SQL escape hatch or maintained assertion
  allowlist.

## Task outline

- [x] Task 1: Cut every first-party SQLx surface over to 0.9 atomically
  - Contract: the workspace owns the sole SQLx version; SQLx remains host-only;
    `macros::sqlx_bridge` remains the sole generated bridge owner;
    `storage::sql` retains native SQLx query types behind the sealed
    `StorageBind` extension traits; SQLx 0.9 argument bounds remain local to
    stores and dialects under ADR-0019.
  - Dynamic SQL contract: ordinary data uses `bind_storage` or the existing
    typed test boundary; non-bindable structural SQL contains only fixed/dialect
    fragments, generated placeholders, or backend-quoted identifiers/literals;
    `AssertSqlSafe` is local to the owning construction/execution seam; no
    production helper accepts arbitrary SQL text.
  - Includes: manifests and lockfile; lifetime-free `Arguments` and
    `IntoArguments`; generated bridge and PostgreSQL array implementations;
    residual SQLx-aware source scanners; every production and test query API
    adaptation; migrations; Post and Syndication Feed queries; visibility and
    feed-event SQL; catalog inspection; backup/restore; PostgreSQL bootstrap;
    raw test fixtures; and accepted SQLx signatures in architecture/decision
    documentation. SQLx 0.9 PostgreSQL option auto-escaping and SQLite driver
    changes receive explicit audits.
  - Verification: the complete host tree compiles after the version change.
    Proc-macro, bridge, typed-bind, source-scanner, and host/wasm isolation
    checks preserve the type and admission boundaries. Focused dual-backend
    query, migration, backup/restore, and transaction tests preserve bind
    ordering, visibility, fresh-database results, historical fixture
    transformations, SQLite connection policy, and PostgreSQL password/option
    behavior. A failing historical-migration fixture proves both schema and
    migration metadata remain unchanged. Delimiter-bearing identifier/literal
    cases prove backend-correct quoting; ordinary-data fixtures use binds.

- [x] Task 2: Prove the complete dependency and backend cutover
  - Depends on: Task 1 compiles and passes its focused behavioral checks.
  - Contract: Cargo.lock contains only SQLx 0.9; Nix continues deriving vendored
    and offline inputs from that lockfile; `sqlx-cli` remains development-only;
    no schema, migration-history, backup-format, or time-library change lands.
  - Verification: the repository-native host/static gate, dual-backend storage
    and server suites, wasm checks, lockfile-derived Nix/offline checks, and
    full backend-by-browser validation pass. Conformance review searches every
    `AssertSqlSafe` occurrence and rejects generic production laundering or
    approved ordinary-data interpolation.

## Risk checks

- Preserve ADR-0001 backend parity and ADR-0021 SQLite transaction shapes; do
  not turn a single-statement mutation into a deferred read-then-write flow.
- Preserve ADR-0071 validation and storability semantics for every generated
  newtype family, including wasm feature isolation and opt-in PostgreSQL arrays.
- Preserve ADR-0169's closed typed bind registry and exact native delegation;
  adapting SQLx syntax must not create a new raw value-admission door.
- Preserve migration ordering, checksums, transaction policy, table identity,
  and fresh/historical results while avoiding reliance on changed SQLx internals
  where a stable 0.9 API exists.
- Treat each `AssertSqlSafe` as a reviewed trust boundary, not a compilation
  fix; keep the safety rationale adjacent to the construction it approves.
- Exercise PostgreSQL quote/literal delimiters and SQLite identifier delimiters,
  plus existing backup/restore and bootstrap escaping cases, on the backend that
  interprets them.
- Update all first-party callsites and obsolete SQLx 0.8 documentation in the
  same clean cutover; leave no compatibility aliases or deprecated paths.
